## How to read this (concepts and terms)

### What is a knowledge graph?

A knowledge graph turns a codebase into a network of **nodes** (things) and
**edges** (relationships between things). Instead of searching files by name or
grepping for strings, you can ask questions like "what calls `applyAction()`?"
or "what connects the engine to the admin UI?" and get answers that span the
entire repo.

### Nodes

Every entity in the codebase becomes a **node**. There are two sources:

| Source | What it captures | Count |
|--------|------------------|-------|
| **AST extraction** | Functions, classes, exports, imports — anything the TypeScript/JavaScript parser can see structurally | 4,660 |
| **Semantic extraction** | Concepts from docs, backlog tasks, config files, API reference HTML — things AST can't parse | 1,407 |

After deduplication the graph has **6,042 unique nodes**.

### Edges

An **edge** is a relationship between two nodes. Each edge has a confidence
level:

| Confidence | Meaning | Example |
|------------|---------|---------|
| **EXTRACTED** (96%) | Explicit in source code — an import, a function call, a direct reference | `deployCard` → `getDeployTarget` (one calls the other) |
| **INFERRED** (4%) | Reasonable inference from context — shared data, same problem domain | `resetColumnHp` ↔ `lastDestroyedCard` (both fix combat rules) |
| **AMBIGUOUS** (<1%) | Uncertain — flagged for human review | Thematic connections that might be coincidental |

Edge types include `calls`, `imports`, `implements`, `references`,
`conceptually_related_to`, `semantically_similar_to`, and `shares_data_with`.

### Communities — what the numbered clusters mean

This is the part that's confusing at first glance. Here's what's happening:

**Communities are automatically detected clusters of tightly connected nodes.**
The algorithm (Louvain community detection) groups nodes that have more
connections to each other than to the rest of the graph. Think of them as
"modules" or "subsystems" that the algorithm discovered by looking at the actual
dependency structure — not the directory layout.

Why this matters:

- **Directory structure lies.** Files in `server/src/` might be tightly coupled
  to files in `engine/src/` but you'd never know from the folder tree.
  Communities show you the *real* module boundaries.
- **Large communities = cohesive subsystems.** A community with 133 nodes (like
  "Server Package Scripts") means those 133 entities are more connected to each
  other than to anything else.
- **Small communities (2-3 nodes) = isolated pairs.** These are leaf nodes or
  utility functions that only talk to each other. The report calls these "thin
  communities" and omits them to reduce noise. There are 891 of them.
- **"Community 123" = unlabeled.** Only the top 30 communities got human-readable
  names. The rest kept their numeric IDs. They're still valid clusters, just
  smaller and less architecturally significant.

### Cohesion scores

Each community gets a **cohesion score** from 0 to 1. This measures how
internally connected the community is:

- **1.0** = every node connects to every other node (perfect clique)
- **~0.5** = moderately connected (typical for mid-size modules)
- **< 0.1** = loosely connected (might deserve splitting)

The report flags low-cohesion communities as potential candidates for
refactoring.

### God nodes

**God nodes** are entities with disproportionately high connectivity
("betweenness centrality"). They sit on the shortest path between many pairs of
nodes, making them architectural bottlenecks or integration points.

In this graph, `applyAction()` is the top god node — it bridges the Bot AI
cluster, the CI verification cluster, the engine core, and several others. This
makes sense: it's the single function that advances game state, so everything
flows through it.

### Surprising connections

These are edges that connect nodes in *different* communities — cross-cutting
concerns that the clustering algorithm didn't expect. They often reveal hidden
coupling (a client component that directly references a server internal) or
important integration points (the combat resolution module feeding data to the
engagement log UI).

### Knowledge gaps

The report lists **isolated nodes** — entities with zero or one connection.
These are either:

- Leaf utilities that nothing depends on (fine)
- Undocumented components with missing edges (worth investigating)
- Generated files that aren't meaningfully connected

The 3,013 isolated nodes here are mostly individual HTML doc pages and small
helper scripts — expected for a 2,000-file repo.

## Usage

### Open the visualization

```bash
open graphify-out/graph.html
```

### Query the graph

```bash
# Broad search (BFS traversal)
graphify query "How does combat resolution work?"

# Trace a specific call chain (DFS)
graphify query "What calls getValidActions?" --dfs

# Shortest path between two concepts
graphify path "MatchManager" "ILedgerStore"

# Plain-language explanation of a node
graphify explain "MCTS"
```

### Rebuild

```bash
# Full rebuild (re-extracts everything)
graphify .

# Incremental (only changed files since last build)
graphify . --update

# Just re-cluster without re-extracting
graphify . --cluster-only
```
