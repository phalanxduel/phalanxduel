# Demo Gate Lessons

These are durable operating lessons for agents preparing a recorded Phalanx Duel demo.

## Stable landing checklist

The demo is not considered green until all of these are true:

- Host-native Postgres is running and project commands select `phalanxduel_development` through `bin/maint/with-dev-postgres.sh` or `bin/maint/with-tooling-postgres.sh`.
- No command inherits the ambient `postgresql:///my` database, and local app work does not start Docker or Colima.
- `pnpm verify:quick` passes.
- `pnpm qa:playthrough:verify` passes with 12/12 scenarios.
- `pnpm qa:visual:run` passes with 3/3 scenarios.
- The worktree is clean, `main` is pushed, and the final push-triggered Pipeline and Code Quality runs are green. In-progress CI is not green.

## Visual baseline discipline

Playwright baselines are platform-specific. Never copy a macOS/Darwin PNG into a Linux baseline. Use the manual `refresh_visual_snapshots=true` workflow input, review the uploaded Linux artifact, and commit the artifact generated by the Linux Playwright environment. Stabilize random visible identities in visual tests before refreshing snapshots.

## Infrastructure boundary

Phalanx Duel's project DB isolation is independent from zdots' `my` database. If `zdots-ctx add-lesson` fails because zdots cannot connect to its ambient socket database, do not bypass the guard or redirect Phalanx commands. Record the failure in the handoff and continue with repo-local agent documentation; repair zdots infrastructure separately.
